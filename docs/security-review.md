# Security review of AEISP itself

AEISP looks for weaknesses in firmware. This review looks at AEISP: what someone, or a misbehaving model,
could do to the lab through the platform. It was done at the end of the project (Phase 17). The fixes are in the
code, and `backend/tests/test_hardening.py` and `backend/tests/test_failures.py` test them.

## What is being protected

| Asset | Why it matters |
|---|---|
| The board | A bad image can brick it until someone holds BOOT. GPIO12/13 are wired to other hardware. |
| The API tokens | The operator token can approve flashing. |
| The Gemini key | It is paid for, and the free tier allows 20 requests a day. |
| The lab history (SQLite, audit chain) | Findings, decisions and approvals must be trustworthy afterwards. |
| The host PC | The backend runs the compiler, Python and USB tools. |

## Who could cause harm

1. **The model.** It sees untrusted text: firmware sources, board replies and fuzz output. It may try any tool with
   any arguments. This is the main threat and it is treated as hostile.
2. **Another program or web page on the same PC.** For example, a page in the browser making requests to
   `127.0.0.1:8000`.
3. **Someone on the local network**, if the backend is started on `0.0.0.0`.
4. **Mistakes**: a pulled cable, a wrong build or a crashed process.

## Controls, and where they live

| Area | Control | Where |
|---|---|---|
| Who can call what | Three role tokens. The comparison takes the same time whatever the input. It fails closed when no token is configured. | `app/security.py` |
| Approvals | Only `operator` can approve. The operator types a confirmation text for each job (`PROMOTE <id>`). Agents have no approve tool. | `app/api/core.py`, `app/tools.py` |
| Flash safety | The pre-flash gate checks the build status, the security scan, size and the source hash. Every flash is followed by verification, and a failure starts a rollback. | `app/deploy/` |
| Board commands | `BOOTSEL`, `HANG` and `REBOOT` are refused for agents and are never generated by the fuzzer. The 3 s watchdog recovers a stuck board. | `app/tools.py`, `app/fuzz/` |
| File access | Project and file names must match strict patterns. `#include` of absolute or `..` paths is refused. Writes are limited to `firmware/workspace/<project>/app`. | `app/build/engine.py` |
| Input size | Every request field has a length limit. Source files are at most 64 KiB. | `app/api/*.py` |
| Model budget | Each run is capped by steps and time. The model client retries rate limits with backoff, and only for the right reasons. | `app/ai/` |
| History | The audit log is a hash chain. Database triggers forbid editing or deleting rows, and `/audit/verify` checks the whole chain. | `app/audit.py` |
| Secrets | `.env` is in `.gitignore`. Tokens are never returned by the API. Confirmation texts are hidden from non-operators on the live feed. | `.gitignore`, `app/api/live.py` |
| Cross-site requests | CORS allows only the Vite dev origin. There are no cookies, so a page cannot ride the user's login. | `app/main.py` |

## Findings and what was done

| # | Finding | Risk | Fix |
|---|---|---|---|
| 1 | The browser's WebSocket sends its token as `/ws?token=...`. Uvicorn's access log printed the whole URL, so the token appeared in the console and in any saved terminal output. | Medium | A logging filter rewrites `token=...` to `token=***` on the uvicorn and AEISP loggers. |
| 2 | There was no limit on wrong tokens, so a local program could guess as fast as it liked. Tokens are 192-bit, so guessing is not practical, but there was also no signal that it was happening. | Low | After 20 wrong tokens in 60 s from one address, that address gets `429` (WebSocket close `4429`) until the window passes. Every refusal is in the audit log. |
| 3 | Responses had no browser security headers. The dashboard could be put inside another site's frame (clickjacking the approval dialog). | Low | Every response now sends `X-Frame-Options: DENY`, `Content-Security-Policy: frame-ancestors 'none'`, `X-Content-Type-Options: nosniff` and `Referrer-Policy: no-referrer`. API answers also send `Cache-Control: no-store`. |
| 4 | An unexpected exception during a flash (for example a USB driver error) could leave the deployment record "running", with no rollback. | Medium | `_flash_and_verify` catches every error. The deployment is closed, and a rollback is attempted. If the board cannot be reached, the message explains the BOOT-button recovery. |
| 5 | The model client's retry wait could not be changed, so its retry rules could not be tested quickly. | Low (testing) | The wait can now be injected. Tests cover timeouts, 429 and 503 being retried, 400 not being retried, and the attempt count. |
| 6 | Could a viewer change anything? | Check | A test walks every non-GET route with the viewer token and requires `403`. |

## Accepted risks

- **One token per role, no user accounts.** This is a single-person lab tool. The audit log records the role,
  not the person.
- **Plain HTTP on localhost.** The tokens cross the loopback interface only. Do not start it with `--host 0.0.0.0`
  on a shared network without a TLS proxy in front.
- **The compiler runs code the model wrote.** That code runs on the board, not on the PC. But the build runs
  CMake and GCC on the host, so a hostile `CMakeLists.txt` would matter. Agents can only write `.c`/`.h` files in
  `app/`, never CMake files.
- **Firmware sources are sent to Gemini.** Do not put secrets in firmware you work on with the AI agents.
